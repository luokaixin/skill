# Dify 工作流说明文档模板

本文档定义了 Dify 工作流说明文档的标准格式。无论是分析已有工作流还是输出新设计的工作流，都必须按此格式产出说明文档。

**设计理念**：文档面向接手运维的人，不是面向开发者。要让人看完就知道"这东西干什么用、怎么跑的、日常怎么维护、哪里有坑"。

---

## 文档结构

一份完整的工作流说明文档包含以下 8 个章节：

| 章节 | 标题 | 核心问题 |
|------|------|---------|
| 0 | 速览 | 这是什么？一句话说清楚 |
| 1 | 工作流逻辑 | 怎么跑起来的？输入什么、怎么处理、输出什么 |
| 2 | 输出字段说明 | 每一项输出是什么、什么格式、给谁用 |
| 3 | 节点配置详解 | 每个节点的每个关键配置项是什么意思、当前值、怎么改 |
| 4 | 运维 / 日常操作 | 最常做的几件事怎么做 |
| 5 | 依赖与配置清单 | 交接时要确认对方拿到什么 |
| 6 | 注意事项 / 踩过的坑 | 哪里容易翻车 |
| 7 | 交接检查清单 | 接手照着核对一遍 |

---

## 0. 速览

**写法**：2-4 句话，用非技术人员能听懂的语言，说清楚这个工作流是干什么的。

**要点**：
- 它是什么（一个XX机器人/一个XX处理流程）
- 它怎么工作（根据什么 → 做什么 → 输出什么）
- 它不是什么（边界声明，如"不是自己编答案的"）
- 如果有多个版本/变体，用一句话说清区别

**示例**：
```
这套工作流是一个在线客服自动答疑机器人。用户在客服窗口提问，系统会：
1. 根据用户所属的项目/游戏，去知识库里找到对应的那份问答资料；
2. 从资料里检索出和用户问题最相关的几条内容；
3. 交给大模型组织成一句自然、简短的客服回复；
4. 判断这个问题机器人能不能自己答——能答就直接回，答不了就标记"需要转人工"。

它不是自己瞎编答案的机器人。所有事实性回答都必须来自知识库。
```

## 1. 工作流逻辑

### 1.1 输入：会传给工作流哪些参数

**写法**：用表格列出 Start 节点的所有输入变量，标注是否必填和作用说明。

**表格格式**：
| 字段名 | 是否必填 | 作用说明 |
|--------|---------|---------|
| text | 必填 | 用户当前这句话（本轮问题正文） |
| project_key | 必填 | 项目标识，用来拼知识库文档名 |
| context | 选填 | 历史对话记录（JSON 字符串） |

**注意事项**：
- 如果变量是外部系统通过 API 传入的，要说明
- 如果有变量定义了但工作流内部没用到，用 > 标注说明原因（预留扩展/历史遗留等）

### 1.2 核心链路

**写法**：用 ASCII 流程图展示完整的执行路径，让人一眼看到数据怎么流的。

**格式规范**：
```
用户输入(start)
   ├─→ 【节点A】功能说明
   │        └─→ 【节点B】功能说明
   │                 └─→ 【汇聚节点】
   ├─→ 【节点C】功能说明 ──┐
   │                        ├─→ 【汇聚节点】
   └─→ 【节点D】功能说明
                            ↓
                    【下游节点】功能说明
                            ↓
                    【输出节点】输出什么
```

**要点**：
- 并行分支用 `├─→` 表示
- 汇聚点要画清楚
- 每个节点标注【节点名称】和一句话功能说明
- 如果有条件分支，标注分支条件
- 末尾用一句话概括整个流程

### 1.3 每个节点在干什么

**写法**：按执行顺序，逐节点说明。每个节点用加粗标题 + 段落说明。

**每个节点必说**：
- 节点类型（Code/LLM/Knowledge Retrieval/IF-ELSE 等）
- 接收什么输入（引用哪个上游变量）
- 做了什么处理（代码逻辑要点 / 提示词核心规则 / 检索配置）
- 输出什么变量
- 如果有问题或特殊设计，用 > 标注

**示例**：
```
**① 项目key游戏key合并（代码节点）** 把 project_key、game_key、game_type 拼成两个知识库文档文件名：
- p_g = {project_key}_{game_key}.csv —— 该游戏的专属问答
- p_t_general = {project_key}_{game_type}_{general}.csv —— 该类型的通用问答

**② LLM（大模型节点）** 拿到检索结果后，按一套客服话术系统提示词生成回复。核心规则：
- 只能根据检索到的 result 回答，知识库里没有的绝不编造；
- 输出是固定的 JSON 格式：{"need_human": 布尔值, "reply": "回复正文"}；
- 内置了防绕过（对抗性防护）。

> ⚠️ 重要提示：context数据清洗节点的产物目前下游没有节点在用，相当于"空转"。
```

### 1.x 版本特有逻辑（如果有变体）

如果工作流有多个版本（如纯文字版/图片版），单独列出每个版本特有的逻辑差异。如果没有变体则省略此节。

## 2. 输出字段说明

**写法**：逐字段说明 End/Answer 节点的每个输出变量，让接手的人明确知道"工作流吐出来的每一项是什么、什么格式、谁在用"。

**表格格式**：
| 输出字段 | 类型 | 格式说明 | 内容示例 | 下游谁在用 |
|---------|------|---------|---------|-----------|
| to_add | string | JSON 字符串，数组内每条含 question + answer | `[{"question":"...","answer":"..."}]` | 人工审核入库系统 |
| duplicates | string | JSON 字符串，数组内每条含 question + answer + matched_question | `[{"question":"...","answer":"...","matched_question":"..."}]` | 人工审核去重列表 |

**每个字段必说**：
- 字段名（对应 End 节点 outputs 里的 variable）
- 数据类型（string / number / array / object）
- 如果是 JSON 字符串，说明内部结构（哪些字段、什么含义）
- 一个真实的内容示例
- 下游谁在消费这个字段（哪个系统/哪个环节）
- 如果字段可以为空，说明什么情况下为空

---

## 3. 节点配置详解

**写法**：逐节点列出关键配置项，每个配置项说明"是什么、当前值、改了会怎样"。这是操作指南的核心，让人知道画布上每个参数是干什么的。

**格式**：每个节点一个小节，内含配置表格。

**示例**：
```
### 3.1 数据准备（Code 节点）

| 配置项 | 当前值 | 说明 |
|--------|--------|------|
| code_language | python3 | 代码语言，一般不用改 |
| 输入变量 faq_list | 来自 start.faq_list | 接收用户传入的 FAQ JSON 字符串 |
| 输入变量 project_key | 来自 start.project_key | 项目标识 |
| 输入变量 game_key | 来自 start.game_key | 游戏标识 |
| 输出 items | array[string] | 解析后的 FAQ 数组，供迭代遍历 |
| 输出 filename | string | 拼出的知识库文档名，格式 {project}_{game}.csv |

### 3.2 检索已有 FAQ（Knowledge Retrieval 节点）

| 配置项 | 当前值 | 说明 |
|--------|--------|------|
| dataset_ids | [实际ID] | 检索的知识库 ID。切换知识库时改这里 |
| retrieval_mode | multiple | 多路召回模式，一般不用改 |
| top_k | 4 | 返回最相关的前 N 条结果。调大=更全但可能带噪音，调小=更准但可能漏 |
| reranking_enable | true | 开启重排序。关闭会降低检索质量 |
| reranking_model | qwen3-vl-rerank | 重排序模型。换模型时改 provider + model |
| query_variable_selector | code_extract.question | 用新 FAQ 的问题作为检索查询词 |

> 💡 改 top_k 的影响：当前 4 条，如果你发现经常漏掉相似 FAQ，可以调到 6-8；如果结果太多导致 LLM 判断混乱，调到 2-3。
```

**要点**：
- 每个节点都要列出，包括 Start 节点的输入变量
- 对每个配置项给出"改了会怎样"的操作指引
- 对容易出错的配置项加 > 标注提醒
- 对需要用户手动修改的配置项（如 dataset_ids、模型 provider）明确标注

## 4. 运维 / 日常操作

**写法**：列出接手后最常做的几件事，每件事说明"改哪里、怎么改、注意什么"。

**常见操作**（按实际工作流选取）：
- 修改提示词 / 回答风格
- 更新知识库内容
- 切换 / 指定使用的模型
- 调整检索参数（top_k、重排序等）
- 出问题时怎么排查（按顺序列出排查步骤）

**排查问题部分**格式：
```
1. 症状描述 → 先怀疑什么 → 怎么确认
2. 症状描述 → 先怀疑什么 → 怎么确认
```

## 5. 依赖与配置清单

### 5.1 插件依赖

| 插件 | 用途 | 用在 |
|------|------|------|
| langgenius/openai | 提供 GPT 模型 | LLM 节点 |
| langgenius/xinference | 提供重排序模型 | 知识检索节点 |

> 注：标注内部插件、账号配置等交接注意事项。

### 5.2 知识库
- 绑定了哪个知识库
- 关键配置（元数据过滤规则、检索模式等）
- 迁移/交接时的注意事项

### 5.3 调用方（上游）
- 谁在调用这个工作流（外部系统/API/手动）
- 输入输出格式约定
- 对接人信息

---

## 6. 注意事项 / 踩过的坑

**写法**：编号列表，每条一个"坑"，说清楚"什么情况 + 为什么 + 怎么避免"。

**常见坑的类型**：
- 多分支提示词不一致问题
- 文件名/命名规则是硬约束
- 某个节点空转/输出未引用
- 输出格式依赖（如 JSON 结构化输出不能关）
- 安全规则不能随意删除
- 版本间差异导致的不一致

**示例**：
```
1. 改话术要改 5 遍（纯文字版） 5 个模型分支的提示词是各存一份的。改客服话术时必须 5 个 LLM 节点全改。
2. 文件名命名规则是硬约束 检索靠文档名精确匹配，文件名差一个字就直接检索不到。
3. 输出是 JSON，不是纯文本 必须保证 LLM 节点的「结构化输出」开着。关掉会导致上游系统解析失败。
```

---

## 7. 交接检查清单

**写法**：`- [ ]` 格式的 checklist，接手人照着逐项核对。

**必含项**：
- [ ] 能登录 Dify，能看到并编辑对应应用
- [ ] 有知识库的编辑权限
- [ ] 确认插件已安装、模型服务可用
- [ ] 知道最关键的几个坑
- [ ] 拿到相关对接人联系方式
- [ ] 自己用真实数据跑通验证一遍

## 使用场景

### 场景一：分析已有工作流

当用户提供一份 Dify DSL YAML 文件让你分析时，按以下步骤产出文档：

1. **解析 YAML**：读取所有节点和边，理清执行流程
2. **识别结构**：找出并行分支、汇聚点、条件分支
3. **提取配置**：记录每个节点的关键配置（模型、提示词要点、代码逻辑、检索参数）
4. **发现问题**：标注空转节点、未引用变量、缺失的错误处理等
5. **按模板输出**：按上述 6 章节格式产出完整文档
6. **附加分析**：在文档末尾附加"架构评价"和"改进建议"章节

### 场景二：输出新工作流

当设计并生成新的工作流 YAML 时，同时产出一份说明文档：

1. 在第四阶段（YAML 生成）完成后
2. 基于设计过程中的所有信息
3. 按上述 6 章节格式产出文档
4. 文档与 YAML 文件一起交付给用户
